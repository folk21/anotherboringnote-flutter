# `STATE.json` schema v1

Every active bounded specification directory has one `STATE.json` file checked into Git. It must be a JSON object with:

| Field | Meaning |
|---|---|
| `schemaVersion` | Integer `1`, rejected if unsupported |
| `specId` | Stable slug identifying the bounded specification |
| `specPath` | Relative path of normative `spec.md` |
| `implementationPath` | Relative path of MAIN-authored `implementation.md` |
| `owner` | Literal `MAIN_AND_HUMAN` |
| `worker` | Current executable worker, initially `AIDER` |
| `platformAcceptance` | Explicit global manual platform status, initially `not-run` |
| `stages` | Ordered list of stage objects |

A stage has unique `id` (`S01`, `S02`, ...), short `title`, `status`, `dependsOn` (prior stage IDs), `evidence` (array of human-readable path/PR/report references), `lastUpdatedBy`, and optional `notes`. Markers in `implementation.md` must exist for every stage. `scripts/spec_state.py validate` ensures stage IDs, paths, dependency direction, evidence type and known statuses are valid. It does **not** verify that attached evidence is true or that all requirements have been met.

## Transitions

| Action | Allowed from | New state | Gate |
|---|---|---|---|
| `start` | `ready`, `blocked` | `in_progress` | All dependencies already accepted |
| `worker-done` | `in_progress` | `verification_pending` | Code prepared for verification, not yet proven |
| `verify` | `verification_pending` | `verified` | `--evidence` required; MAIN/developer owns truth |
| `accept` | `verified` | `accepted` | Additional `--evidence` human review required |
| `block` | `ready`, `in_progress`, `verification_pending`, `verified` | `blocked` | Explain with `--evidence` |

A draft initially generated by MAIN may legitimately begin at `verification_pending` to mean “implementation exists; execution of Flutter checks pending”. This does not bypass acceptance. Changes and evidence additions are committed on a feature branch after review; worker never directly writes state.

## Evolution policy

Do not change the JSON shape casually. To add fields or change transition semantics, create a reviewed active workflow specification, migrate existing files explicitly, update validation and tests, and increment `schemaVersion` if backward-incompatible. Chat and local worker logs are not substitutes for version-controlled state. The schema is local to this project and needs reconciliation with the latest SignalHarvester reference when that file becomes available.
